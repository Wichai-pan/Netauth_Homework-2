\begin{abstract}
We created an encrypted 4096-bit RSA root certification authority (CA) on Kali Linux,
generated a separate 2048-bit RSA key and certificate signing request (CSR) on an Ubuntu
Flask server, and issued a three-year TLS server certificate. We then configured the
existing web application to serve HTTPS on port 8443. OpenSSL verified the certificate
chain, a client request using the root certificate returned HTTP 200, and Firefox
accepted the connection after the laboratory root CA was imported. The server private
key remained on Ubuntu; the root CA private key remained on Kali.
\end{abstract}

\section{Objective and laboratory environment}
The objective was to protect communication with the existing SEC-LAB Flask application
using TLS and a certificate issued by a laboratory CA. The application was initially
served over unencrypted HTTP on port 5000. We retained that configuration until the
certificate had been created and verified, then changed the Flask startup configuration
to serve HTTPS on port 8443. Table~\ref{tab:topology} records the laboratory roles.

The CA key and certificate were stored under \texttt{ca/} on Kali. The server key and
CSR were created under \texttt{server/} on Ubuntu. Only the CSR was sent to Kali for
signing; only the issued certificate was sent back to Ubuntu. Neither private key was
transferred between machines.

\section{Part I: Create and inspect the root CA}
On Kali, we created a dedicated working directory and generated an AES-256-encrypted
4096-bit RSA private key with \texttt{openssl genrsa -aes256}. We restricted its file
permissions to mode 600. The private-key passphrase was required again when creating
the root certificate and issuing the server certificate; it is not included in this
report. No private-key dump is reproduced here.

\section{Part II: Generate the server key and CSR}
On Ubuntu, we generated a separate 2048-bit RSA private key and set its permissions to
mode 600. The CSR configuration specified \texttt{C=ES}, \texttt{O=NETAUTH}, and
\texttt{CN=netauth.server}. Its requested subject alternative names (SANs) were
\texttt{DNS:netauth.server} and \texttt{IP:192.168.1.35}. OpenSSL reported
\texttt{Certificate request self-signature verify OK}, confirming that the CSR was
signed by the server's private key. We transferred \texttt{server.csr} to Kali via SCP
and verified it again there. The server's \texttt{server.key} stayed on Ubuntu.

\section{Part III: Issue and verify the server certificate}
On Kali, the CA extension file set critical \texttt{CA:FALSE}, digital-signature and
key-encipherment usage, and \texttt{serverAuth} extended key usage. The handout's CSR
example names \texttt{netauth.server}, whereas its final checklist also asks for
\texttt{sec-lab.local}. We retained the originally requested name and added
\texttt{DNS:sec-lab.local} to the CA's issuance extensions. Therefore, the final
certificate contains both DNS names and \texttt{IP:192.168.1.35}. This addition was
made during CA issuance; the original CSR was not altered.

Using the root CA key, we issued a server certificate valid for 1095 days
(approximately three years), shorter than the root certificate's validity. The final
certificate has subject \texttt{C=ES, O=NETAUTH, CN=netauth.server}, issuer
\texttt{SEC-LAB Root CA}, \texttt{CA:FALSE}, and TLS Web Server Authentication usage.
The verification command and its observed result were:

\begin{lstlisting}
openssl verify -CAfile ca/rootCA.crt server/server.crt
server/server.crt: OK
\end{lstlisting}

\section{Part IV: Deploy HTTPS and establish browser trust}
We copied the issued \texttt{server.crt} back to Ubuntu. The public key extracted from
that certificate and the public key derived from \texttt{server.key} produced identical
SHA-256 hashes, confirming that the certificate matched the private key on the server.
After backing up \texttt{app.py}, we changed its Flask startup block to load
\texttt{server/server.crt} and \texttt{server/server.key} on port 8443 with debug mode
disabled. The \texttt{sec-lab} service restarted and remained active.

\begin{lstlisting}
app.run(host="0.0.0.0", port=8443,
        ssl_context=("server/server.crt", "server/server.key"),
        debug=False)
\end{lstlisting}

From Kali, the following request used the laboratory root certificate to validate
the server's chain and address. It returned \texttt{HTTP/1.1 200 OK}:

\begin{lstlisting}
curl --cacert ca/rootCA.crt -I https://192.168.1.35:8443/
\end{lstlisting}

Firefox initially warned about the untrusted local CA. We imported only
\texttt{rootCA.crt} into Firefox's Authorities store and enabled trust for identifying
websites. We did not add a site-specific security exception. After reloading,
Firefox displayed the Flask application at \url{https://192.168.1.35:8443/}.
Its certificate viewer showed \texttt{netauth.server} issued by
\texttt{SEC-LAB Root CA}; the SAN included the IP address used in the URL.

\section{Questions and answers}
\begin{enumerate}[leftmargin=*,label=\textbf{\arabic*.}]
\item \textbf{Why protect the root CA private key more carefully than its certificate?}
The private key can sign arbitrary certificates that clients may accept as issued by
this CA. The root certificate contains the public key and is intentionally distributed
to clients. Disclosure of the certificate does not grant signing capability.

\item \textbf{Why is the root CA certificate self-signed?}
It is the trust anchor and has no superior CA in this laboratory hierarchy. Its own
signature confirms internal consistency; actual trust comes from explicitly installing
the root certificate on the client.

\item \textbf{What is in a CSR, and why does the CA not need the server private key?}
The CSR carries the subject, public key, requested attributes such as SANs, and a
signature made with the corresponding server private key. The CA verifies the request
using the public key and signs the resulting certificate with the CA key. The server
private key never needs to leave Ubuntu.

\item \textbf{What does the CA signature guarantee?}
It binds the signed certificate fields, including the subject and public key, to the
issuing CA and allows a client to detect modifications. A client must also trust the
CA, check validity and name matching, and rely on the CA's identity checks; the
signature alone does not prove that the server software is secure.

\item \textbf{Why must the server certificate have \texttt{CA:FALSE}?}
It identifies the certificate as an end-entity certificate and prevents it from being
accepted as a subordinate CA for signing other certificates.

\item \textbf{What is the purpose of \texttt{serverAuth}?}
This extended key usage authorizes the certificate for TLS server authentication,
which is the purpose required for the HTTPS endpoint.

\item \textbf{Why is SAN important for HTTPS validation?}
Clients match the host name or IP used in the URL against SAN entries in the server
certificate. The common name alone is not sufficient for modern HTTPS name checking.

\item \textbf{What if the client uses an IP absent from SAN?}
The client reports a certificate name mismatch and rejects or warns about the
connection, even when the issuing root CA is trusted.

\item \textbf{Why does installing \texttt{rootCA.crt} change Firefox's decision?}
It makes the root CA a local trust anchor. Firefox can then validate the server
certificate's signature and chain against that root; it still checks the date,
intended use, and requested address.

\item \textbf{Would HTTPS protect the password database after server compromise?}
No. TLS protects data in transit between browser and server. A compromise of the
server can expose files, application data, and private keys on the server; separate
at-rest protection, access control, and hardening are required.
\end{enumerate}

\section{Conclusion and submitted artifacts}
The original application was successfully served over HTTPS on port 8443 with a
certificate issued by the laboratory root CA. Both OpenSSL and Firefox validated the
final chain, and the browser warning disappeared only after the root certificate was
trusted. The result protects the client--server channel; it does not repair the
application's intentionally insecure authentication or protect server-side data after
a host compromise.

The accompanying \texttt{artifacts/} directory contains the root certificate,
server CSR, server certificate, and both OpenSSL configuration files. No private
keys are included.
